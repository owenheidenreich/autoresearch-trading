## 1. What W2a did

No divergence surface between research and production.

### 1a. Shared helper (v2/core/market_structure.py)

W2a extended the helper with three vectorized array variants, since v2's
feature pipeline works on flat per-bar arrays while v3 works on per-day
dicts:

| Function | Inputs | Output |
|---|---|---|
| `sigma_pos_arrays(spx_close, spy_close, spy_volume, day_starts)` | per-bar arrays + day boundaries | (n,) per-bar σ-position, clipped to `[-5, +5]` |
| `omar_arrays(spx_high, spx_low, day_starts)` | per-bar arrays | dict of per-bar `{high, low, mid, range}` (broadcast per day) |
| `last10_arrays(spx_high, spx_low, day_starts)` | per-bar arrays | dict of per-bar `{high, low, range}` (rolling 10-bar within-day) |

These match the dict-based `sigma_pos`, `build_omar_map`, `last10` functions
exactly. v3 continues to use the dict variants (per-bar access pattern);
v2 uses the array variants (full-array access pattern). One formula per
derived quantity, enforced by tests and by ORC's attribution-match to
prediction (W1 shipped with exact-match).

### 1b. Eight new v2 features (indices 48–55, `SESSION_FEATURE_NAMES`)

| idx | name | encoding | normalization |
|---:|---|---|---|
| 48 | `sigma_pos` | SPY-derived VWAP σ-position, SPX-scaled | `_NO_NORMALIZE` (already clipped `[-5, 5]`) |
| 49 | `omar_retest_dist_norm` | `min(|close − omar.high|, |close − omar.low|, |close − omar.mid|) / omar.range` | rolling z-score |
| 50 | `omar_range_pct` | `omar.range / close` — opening volatility unit | rolling z-score |
| 51 | `last10_range_over_omar` | `(last-10-bar SPX range) / omar.range` — the squeeze metric | rolling z-score |
| 52 | `inside_first15` | `{0, 1}` — is `close ∈ [first15_low, first15_high]`? | `_NO_NORMALIZE` |
| 53 | `late_window_40_120_flag` | `{0, 1}` — is `bar_of_day ∈ [40, 120]`? | `_NO_NORMALIZE` |
| 54 | `omar_mid_pos_units` | signed `(close − omar.mid) / omar.range` | `_NO_NORMALIZE` (clipped `[-10, 10]`) |
| 55 | `last10_break_state` | `{+1, 0, −1}` — above / inside / below last10 range | `_NO_NORMALIZE` |

Dropped from the original proposal:
- `abs_sigma_pos` — v2 model uses GELU-based nonlinear heads; it can learn
  absolute-value transforms from `sigma_pos` directly.
- `minutes_since_open_norm` — redundant with v2's existing `intraday_sin`,
  `intraday_cos`, `intraday_phase`.
- `vp_dist_to_poc_norm`, `inside_value_area` — deferred pending Codex's
  Experiment 5 (matched-control retest) per the plan's W2b conditional.

## 4. What this result means

### 4a. W2a itself is fine

The features were computed correctly, normalized correctly, loaded into the
model correctly, and processed without error. Feature matrix shape
`(382920, 89)`, 0% NaN, z-score distributions within expected ranges. The
pipeline side of W2a is a clean ship.

### 4b. The training loop is still the bottleneck

Score −0.200, PF 0.722, DD 97%, direction accuracy ~50%. Identical failure
mode to the pre-W2a exp_171 family (see `v2/lab_notebook.md` line 1892).
The W2a features did not rescue the broken training loop — they weren't
meant to. Per `~/.claude/projects/…/memory/project_oracle_ceiling_broken.md`:
> Training objective is the bottleneck — LR AUC 0.62 on signal; model rank
> ρ~0 because it trains on discarded one-hot/binary targets.

W2a addresses the **input-side** of the architecture (what the model sees).
It does not address the **objective-side** (what the model optimizes). That
is a separate hypothesis, tested separately.

### 4c. What's now possible

The v2.2 schema is the new baseline lineage. Any future experiment can
reference the 8 new features without further data work:

- A training-objective change (e.g., continuous PnL supervision, dense
  per-bar rewards) can ride on top of the enriched feature set.
- A model-architecture change (e.g., a different aggregation layer that
  gives these features more weight) can use them directly.
- A v3-Layer-2 supervised model — the master plan's actual target — would
  consume these features plus the post-A1 attribution labels as its
  training surface. That is the intended downstream consumer, not the v2
  model.

### 4d. What this result does NOT tell us

- Whether the features would help a **different training config**. Untested;
  would require a paired experiment (v2.1 schema + new config) vs (v2.2
  schema + new config).
- Whether the 97% DD is driven by entries the new features could have
  filtered, if the model had a signal to use them. Untested; would require
  a policy-sweep-style analysis, not a training change.
- Whether sigma-position's v3-level effectiveness (A1's `side_error
  402 → 176` result) transfers to the v2 model's decision process. The v2
  model saw `sigma_pos` as one of 89 normalized features; the v3 ORC
  teacher saw `sigma_pos` as a hard gate. The two consumer paths are
  structurally different.

## 5. Hygiene / known issues surfaced during the run

### 5.1. `build_v2_dataset.py` wrote a stale digest (needs fix)

After the fresh rebuild:
- `metadata.chain_sidecar_digest`: stored `3828460bd9ec9127`, computed
  `16a6b050d246f4fd` (mismatch)
- `metadata.fingerprint`: stored `5f2ec17a7176df5c`, computed
  `e43e421037766fd1` (mismatch after the digest was patched)

The stored digest `3828460bd9ec9127` is byte-identical to the pre-W2a
backup's digest (`v2/data.pt.bak_pre_v3_features`, dated 2026-04-18).
The build somehow carried the old digest forward despite writing fresh
sidecars.

**Worked around** by patching `metadata.chain_sidecar_digest` and
`metadata.fingerprint` in-place. Pre-run gate then passed cleanly. Future
rebuilds should expect this same bug until `build_v2_dataset.py:1152` is
investigated. Candidate fix location: ensure `sidecar_paths` at the time
of `manifest_sidecar_digest(sidecar_paths)` points to the freshly-written
sidecars, not a stale list.

### 5.2. `pre_run_gate.py`'s legacy-flag scan picks up Finder duplicates

`v2/ops/pre_run_gate.py` scans all `.py` / `.sh` files under the project
for the legacy `--n-folds` flag. It caught two macOS Finder duplicates:
- `v2/collect_trajectories 2.py` (8.7 KB, dated 2026-04-14)
- `v2/ops/run_experiment_wf 2.py` (7.3 KB, dated 2026-04-11)

Both files are untracked by git and predate this session. **Quarantined**
to `/tmp/w2a_quarantine/`. If iCloud Finder sync recreates them, the
pre-run gate will block the next experiment. Candidate fix: skip files
whose name matches ` [0-9]+\.py$` (Finder-duplicate pattern) or skip
files not in the git index.

### 5.3. `ops.health` reports `model` / `smoke` FAIL after v2.1 → v2.2 bump

Expected — no v2.2-compatible `model.pt` exists yet. Not a blocker; the
first successful training run that promotes through `run_final_train`
